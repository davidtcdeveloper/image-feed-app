# **Architectural Evaluation and Migration Strategy: Transitioning Kotlin Multiplatform Projects from Koin to Metro**

The landscape of dependency injection (DI) in Kotlin Multiplatform (KMP) development has reached a significant architectural inflection point. Historically, teams have relied heavily on runtime service locators such as Koin due to their straightforward setup, quick initial implementation, and lack of compilation overhead.1 However, as multiplatform codebases scale in module count, team size, and complexity, runtime resolution introduces substantial stability risks.1 The absence of compile-time verification means that graph misconfigurations, circular dependencies, or missing bindings remain latent until they trigger runtime crashes during application execution or user navigation.1  
Metro addresses these stability and scaling challenges.3 It is a compile-time dependency injection framework designed specifically for Kotlin and implemented entirely as a native Kotlin compiler plugin.5 By operating directly on the Frontend Intermediate Representation (FIR) and Intermediate Representation (IR) phases of the Kotlin K2 compiler, Metro bypasses the traditional source-generation cycles associated with Kotlin Symbol Processing (KSP) or Kotlin Annotation Processing Tool (KAPT).7 It validates the entire dependency graph at compile-time and lowers directly into highly optimized platform bytecode.1 This document provides a rigorous architectural evaluation of Metro and delivers a comprehensive, production-ready migration strategy to transition an active Kotlin Multiplatform project from Koin to Metro.

## **Architectural Foundations of Metro**

To successfully transition a codebase from Koin's runtime model, the underlying compilation and resolution mechanisms of Metro must be thoroughly understood. Metro is inspired by the design paradigms of Dagger, Anvil, and Kotlin-Inject, but it is built from the ground up to leverage the compiler plugin architecture of modern Kotlin.3

### **Compiler Integration and Resolution Performance**

Unlike traditional compile-time frameworks like Dagger, which rely on KAPT or KSP to generate intermediate Kotlin source files that must then be compiled in a secondary compiler round, Metro integrates directly into the compiler frontend.3 This is achieved using FIR for diagnostic analysis and static graph validation, combined with IR transformers for direct code generation.7 Consequently, Metro avoids extra compiler frontend invocations, yielding significant build performance advantages.3 At compile-time, Metro performs topological sorting with active cycle detection across all declared bindings.7 If a cycle or missing dependency is identified, the compiler halts the build and emits actionable error diagnostics with detailed resolution paths, eliminating runtime injection failures.1  
At runtime, Metro's performance characteristics match hand-written, direct constructor invocations.1 The framework avoids the map lookups, dynamic reflection-like metadata queries, and concurrent lock allocations inherent in Koin's service-location registry. To enforce lifecycles and scope singletons, Metro uses lean provider factory classes and optimized double-checked locking patterns (DoubleCheck) within the generated bytecode, ensuring minimal memory footprint and zero execution-time overhead.3

### **Structural Contrast with Alternative Compile-Time Frameworks**

The structural differences between Metro and other compile-time dependency injection solutions highlight its design choices and multiplatform-first philosophy.3

| Feature Dimension | Metro | Dagger (Hilt) | Kotlin-Inject |
| :---- | :---- | :---- | :---- |
| **Metaprogramming Tool** | Native K2 Compiler Plugin (FIR/IR) 7 | KAPT / KSP (Source Code Generation) 3 | KSP (Source Code Generation) 1 |
| **Kotlin Multiplatform** | First-class, native support for all JVM, JS, Wasm, and Native targets 5 | Unsupported natively (restricted to JVM/Android) 2 | Supported across multiplatform targets 1 |
| **Module Declaration** | No @Module annotation; uses graph supertypes and @BindingContainer interfaces 3 | Verbose abstract @Module classes with explicit @InstallIn directives 3 | Composition via abstract classes and interface inheritance 3 |
| **Platform Injections** | Constructor, assisted, and member injection; top-level functions 3 | Member injection restricted to classes; no top-level function injection 3 | Property and function injection; restricted member injection features 3 |
| **Private Member Access** | Can inject private constructors, properties, and functions directly 3 | Prohibited; injected members and constructors must be package-private or public 3 | Restricted visibility rules; compiler boundaries limit private injection 3 |
| **Optional Dependencies** | Supported natively via standard Kotlin constructor default parameters 3 | Verbose declaration required via @BindsOptionalOf interfaces 3 | Manual implementation required; no direct native constructor default support 3 |

## **Compile-Time Graph Construction and Metadata Mechanics**

To maintain safety and support features like optional dependencies and private injections, Metro implements a sophisticated code generation and serialization architecture.3

### **Provider Factory Generation and Private Member Access**

During compilation, Metro generates a dedicated Provider factory class for every constructor-injected type, @Provides function, or @Binds declaration.3 Because these factories must sometimes resolve types with private constructors or access private properties, Metro generates them as nested classes directly within the target structures.3 This design preserves Kotlin visibility scoping while allowing the generated DI code to bypass standard class-access restrictions.3  
Furthermore, if a dependency constructor defines a default parameter value (indicating an optional dependency), Metro copies the default value expression directly into the generated nested factory class.3 This enables optional parameters to refer to private APIs inside the declaring class without exposing those APIs to the rest of the application module.3

### **Serialization and Downstream Graph Assembly**

Metro uses an incremental compilation strategy to build dependency graphs across multi-module projects.10 To communicate binding information between compiled modules without re-analyzing the original source code, Metro generates custom binary metadata.9

* **MetroMetadata Serialization:** Metro serializes the available providers, parent graphs, binding targets, and parameter layouts into custom @MetroMetadata annotations embedded directly within Kotlin’s compiled .class metadata.11  
* **Accessor Functions:** For every extendable parent graph, the compiler plugin generates specialized internal bridge functions suffixed with \_metroAccessor.9 These functions expose the underlying provider fields and instance allocations.9  
* **Downstream Resolution:** When compiling a downstream child graph or module, the compiler reads the serialized @MetroMetadata of upstream dependencies, extracts the required symbols, and routes downstream resolutions through the generated \_metroAccessor bridge functions, ensuring secure and stable compilation boundaries.9

## **Infrastructure Integration and Gradle Configuration**

Integrating Metro into a Kotlin Multiplatform project involves removing Koin's runtime plugins, configuring the compiler plugin, and resolving multiplatform classpath interactions.4

### **Platform Compatibility and Stability Tiers**

Metro’s compiler plugin targets a wide, moving compatibility window of Kotlin compiler versions, usually supporting the current stable release and up to two subsequent incremental updates (N+2 compatibility).12 The multiplatform runtime components target Kotlin languageVersion and apiVersion 2.2.12 To help developers assess feature readiness, Metro categorizes its components into explicit stability tiers.10

| Stability Tier | Core Components | Operational Status |
| :---- | :---- | :---- |
| **Tier 1 (Core & Production Ready)** | Graph validation, compiler code generation, runtime factories, multiplatform targets, incremental compilation, IDE integration for stable Android Studio/IntelliJ 10 | Fully stable, production-validated, and covered by comprehensive test suites.10 |
| **Tier 2 (Diagnostics & Reporting)** | Performance tracing, JSON dependency reporting, build visualization, reportsDestination exports 10 | Fully functional but subject to potential API changes in major releases.10 |
| **Tier 3 (Experimental / Preview)** | Integration with preview and canary versions of IDEs (IntelliJ EAP, Android Studio Canary) 10 | Best-effort support; compiled on demand with potential for temporary regressions.10 |

### **Gradle Configuration and Compilation Setup**

The Metro Gradle plugin is applied to the root build file and configured individually within each multiplatform module.4

### **Resolving the KSP Classpath Ordering Issue**

In complex Kotlin Multiplatform projects that utilize both Metro and KSP (for example, using Room or another processor alongside Metro), a classpath compilation conflict can occur.13 Because KSP generates code into target-specific directories (such as the JVM source set) late in the compilation pipeline, Metro's graph generation task—which processes common code first—may run before KSP outputs its generated types.13 This leads to compilation failures where Metro reports missing bindings for types that KSP has not yet generated.13  
To resolve this issue, the Gradle build must explicitly bind KSP's source generation to the metadata compilation phase.13 The build team must configure the KSP tasks to depend on common metadata generation and manually include the generated directories in the common source set.13

Kotlin  
tasks.withType\<com.google.devtools.ksp.gradle.KspTaskCommonClassifiers\> {  
    // Force KSP compilation to align with common main metadata generation   
    dependsOn("kspCommonMainKotlinMetadata")   
}

kotlin.sourceSets.commonMain {  
    // Explicitly add KSP generated directories to the common source set   
    kotlin.srcDir("build/generated/ksp/metadata/commonMain/kotlin")   
}

## **Comprehensive Component Mapping from Koin to Metro**

Migrating a codebase requires translating dynamic Koin runtime registrations into explicit, statically validated compile-time structures in Metro.1

### **Paradigm Mapping and API Translation**

The table below maps common Koin constructs to their compile-time equivalents in Metro:

| Koin API Expression | Metro Equivalent Construct | Structural Rationale |
| :---- | :---- | :---- |
| single { Impl() } | @SingleIn(Scope::class) \+ @Inject | Instructs the compiler to generate a double-checked singleton provider factory for the scoped lifetime.3 |
| factory { Impl() } | Unscoped class with @Inject | Unscoped bindings are treated as factory declarations, instantiating a new instance on every request.3 |
| single\<Interface\> { Impl() } | @ContributesBinding(Scope::class) | Statically registers the concrete implementation class as the provider for the specified interface type.2 |
| get() | Explicit constructor parameter | Dependencies are declared directly as constructor parameters, allowing the compiler to validate parameter types.1 |
| by inject() | Lazy\<T\> | Defers initialization until first access using Kotlin's native Lazy\<T\> type, backed by Metro's provider stitching.3 |
| factory { (param: Type) \-\> Impl(param) } | @AssistedFactory | Generates a compile-time factory interface for passing runtime parameters alongside injected dependencies.3 |
| module {... } | @BindingContainer | Defines a reusable compile-time binding module containing @Provides and @Binds declarations.9 |

### **Declarative Dependency Graph Architecture**

In Metro, dependency graphs are defined using interfaces annotated with @DependencyGraph.11 When a graph requires external runtime inputs (such as an application configuration or a platform database driver), these inputs are provided via a @DependencyGraph.Factory interface.11

Kotlin  
import dev.zacsweers.metro.DependencyGraph  
import dev.zacsweers.metro.Provides  
import dev.zacsweers.metro.Scope  
import dev.zacsweers.metro.SingleIn  
import dev.zacsweers.metro.Inject  
import dev.zacsweers.metro.BindingContainer

@Scope  
annotation class AppScope

interface ApiService

class ApiServiceImpl @Inject constructor(  
    private val httpClient: HttpClient  
) : ApiService

@BindingContainer  
interface NetworkModule {  
    @Provides  
    fun provideHttpClient(): HttpClient \= HttpClient()  
}

@SingleIn(AppScope::class)  
@DependencyGraph(  
    scope \= AppScope::class,  
    bindingContainers \= \[NetworkModule::class\]  
)  
interface ApplicationGraph {  
      
    // Expose dependency lookups to non-DI components (e.g., UI or entry points)   
    val apiService: ApiService  
    val appConfig: AppConfig

    @DependencyGraph.Factory  
    fun interface Factory {  
        // Parameters marked with @Provides inject runtime instances directly into the graph   
        fun create(  
            @Provides config: AppConfig  
        ): ApplicationGraph  
    }  
}

### **Implementing Graph Instances**

To instantiate dependency graphs, Metro uses compiler intrinsics that generate the concrete graph implementations at compile-time.2

* **Parameterless Graphs:** For simple graphs that require no external runtime configuration, the parameterless createGraph\<T\>() intrinsic is used.2  
* **Parameterized Graphs:** For graphs that require runtime arguments, the createGraphFactory\<F\>() intrinsic is used to retrieve the factory implementation, which is then invoked with the required arguments.2

Kotlin  
import dev.zacsweers.metro.createGraph  
import dev.zacsweers.metro.createGraphFactory

fun initializeApplication() {  
    // Option A: Instantiating a parameterized graph via its factory   
    val runtimeConfig \= AppConfig(environment \= "Production")  
    val graphWithFactory \= createGraphFactory\<ApplicationGraph.Factory\>().create(runtimeConfig)  
      
    // Option B: Instantiating a parameterless graph directly   
    // val simpleGraph \= createGraph\<SimpleApplicationGraph\>()  
      
    val service \= graphWithFactory.apiService  
}

### **Integrating Dynamic Provider Intrinsics**

Metro integrates with Kotlin’s native language types to handle lazy and deferred dependencies, removing the need for custom framework-specific wrappers.3

Kotlin  
import dev.zacsweers.metro.Inject

class SessionController @Inject constructor(  
    // Evaluates lazily on first access and caches the result thereafter   
    private val databaseLoader: Lazy\<DatabaseDriver\>,  
      
    // Generates a new instance on every invocation of the function provider   
    private val networkClientFactory: () \-\> HttpClient,  
      
    // Standard Kotlin function types can be combined with Lazy to inject deferred factories   
    private val deferredServiceFactory: () \-\> Lazy\<AuthService\>  
) {  
    fun executeLoad() {  
        if (databaseLoader.value.isReady()) {  
            val client \= networkClientFactory()  
            client.connect()  
        }  
    }  
}

On the JavaScript target (Kotlin/JS), the platform runtime cannot implement the standard functional interface for Provider\<T\> directly due to native JS target limitations.8 Metro handles this limitation transparently by generating call-site adapters to compile functional injections cleanly across both JVM and JS targets.8

### **Subcomponent Hierarchy and Scoped Graph Extensions**

To model hierarchical lifecycles (such as nested scopes or transient user sessions), Metro uses @GraphExtension interfaces.2 Graph extensions are child graphs that inherit all bindings from their parent graph while introducing their own scoped dependencies.3

Kotlin  
import dev.zacsweers.metro.GraphExtension  
import dev.zacsweers.metro.Provides  
import dev.zacsweers.metro.Scope  
import dev.zacsweers.metro.SingleIn

@Scope  
annotation class SessionScope

@SingleIn(SessionScope::class)  
@GraphExtension(scope \= SessionScope::class)  
interface SessionGraph {  
      
    val sessionToken: String

    @GraphExtension.Creator  
    fun interface Creator {  
        fun create(  
            @Provides sessionToken: String  
        ): SessionGraph  
    }  
}

@DependencyGraph(scope \= AppScope::class)  
interface MainAppGraph {  
    // Child graph extensions must be exposed via a factory accessor in the parent graph   
    val sessionGraphCreator: SessionGraph.Creator  
}

When referencing graph extensions, casting the extension interface to parent supertypes is not supported.14 Because graph extensions are constructed in the context of their specific parent graphs and can define custom downstream merging, replacement, or exclusion rules, they do not share direct subtype hierarchies.14

### **Critical Development Pitfalls and Compiler Constraints**

When structuring multi-module projects in Metro, several compilation constraints must be observed to avoid build failures.

#### **The Internal Visibility Aggregation Failure**

Metro uses compile-time aggregation to automatically collect classes annotated with @ContributesBinding into the target graph.5 However, this aggregation introduces a strict visibility requirement 2:  
If an implementation class is declared with internal visibility in a multi-module project structure, Metro's compiler plugin will generate glue code in the downstream graph module that attempts to reference the implementation class by name.2 Because internal classes are invisible across module boundaries, this generated code fails Kotlin’s visibility checks.2  
The compiler will emit a misleading MissingBinding error naming the target interface rather than pointing to the implementation visibility mismatch.2  
**Resolution:** Any class annotated with @ContributesBinding that is aggregated into a graph in a separate module must be declared with public visibility.2

#### **The Deep Extension Path Limit Failure**

When designing nested lifecycles, developers must avoid deeply nested @GraphExtension chains (for example, chaining 10 or more levels of extensions).15 Because Metro generates the implementation of each @GraphExtension as an inner class of its parent graph's implementation, the generated .class filename grows linearly with the chain depth (e.g., AppGraph\_Impl$SessionGraph\_Impl$FeatureGraph\_Impl...).15  
This can eventually exceed the filename segment limits of the underlying filesystem (typically 255 characters), causing the compiler to fail with a misleading Permission denied error.15 Designers should limit nested lifecycles to three or four levels, bridging transient states through parallel graphs or explicit factories where possible.

#### **The Graph Inheritance Restriction**

Metro enforces strict compilation rules on inheritance hierarchies 2:  
An interface annotated with @DependencyGraph is prohibited from extending another interface that is also annotated with @DependencyGraph.2 The compiler plugin will reject this arrangement with the diagnostic message: *"Graph class may not directly extend graph class"*.2  
**Resolution:** To share bindings or expose platform-specific leaf implementations, define the base structure as a plain interface without the @DependencyGraph annotation.2 Annotate only the final platform-specific implementation with @DependencyGraph.2

## **Structured Migration and Coexistence Phases**

Transitioning an active, production-scale Kotlin Multiplatform application from Koin to Metro should be executed in planned, incremental phases to ensure code stability and maintain development velocity.

### **Phase 1: Coexistence and Integration Bridge**

During the initial phase of the migration, both DI frameworks must run concurrently in the codebase.6 This approach avoids a massive, single-commit refactor and allows the team to verify the compilation of both pipelines in parallel.

Kotlin  
// \--- Step A: Identify a leaf repository currently registered in Koin \---  
// class UserRepository(private val apiService: ApiService)  
// val koinModule \= module { single { UserRepository(get()) } }

// \--- Step B: Convert the repository to use Metro constructor injection \---  
import dev.zacsweers.metro.Inject  
import dev.zacsweers.metro.SingleIn

@SingleIn(AppScope::class)  
class UserRepository @Inject constructor(  
    private val apiService: ApiService  
)

// \--- Step C: Bridge the Metro-constructed instance back into Koin \---  
val networkBridgeModule \= module {  
    // Instantiate the application graph using the compiler intrinsic   
    single\<ApplicationGraph\> {  
        createGraphFactory\<ApplicationGraph.Factory\>().create(get\<AppConfig\>())  
    }  
      
    // Delegate the Koin request to the verified Metro graph  
    single\<UserRepository\> { get\<ApplicationGraph\>().userRepository }  
}

### **Phase 2: Systematic Module Extraction**

Once the core graph and bridging mechanisms are established, development teams should systematically migrate Koin modules to Metro @BindingContainer structures or class-level @Inject declarations.

  \+-----------------------------------------------------------------+  
  |                      Phase 1: Coexistence                       |  
  |  \- Both Koin and Metro run in parallel             |  
  |  \- Leaf dependencies migrated to Metro \`@Inject\`   |  
  \+-----------------------------------------------------------------+  
                                  |  
                                  v  
  \+-----------------------------------------------------------------+  
  |                   Phase 2: Systematic Migration                 |  
  |  \- Convert Koin modules to Metro \`@BindingContainer\`      |  
  |  \- Bridge dependencies between frameworks         |  
  \+-----------------------------------------------------------------+  
                                  |  
                                  v  
  \+-----------------------------------------------------------------+  
  |                   Phase 3: Static Verification                  |  
  |  \- Remove Koin library and dependencies from build              |  
  |  \- Enable strict compile-time diagnostic checks   |  
  \+-----------------------------------------------------------------+

The table below outlines the execution steps for each phase of the migration:

| Phase | Core Objective | Key Action Items | Risk Mitigation Strategy |
| :---- | :---- | :---- | :---- |
| **Phase 1: Coexistence** 6 | Establish the core Metro graph while keeping Koin as the primary registry. | Apply the Metro Gradle plugin 4; declare custom scopes 11; migrate leaf classes to @Inject constructor injection.5 | Keep Koin running as the primary runtime coordinator; route leaf class requests through Metro graph delegates. |
| **Phase 2: Extraction** | Systematically migrate Koin modules to Metro modules. | Convert Koin modules to @BindingContainer interfaces 9; replace dynamic runtime lookups with compile-time interfaces. | Run continuous integration builds to verify graph compilation after migrating each module. |
| **Phase 3: Enforcing Safety** 8 | Fully remove Koin and enable strict compile-time validation. | Remove Koin Gradle dependencies; set desugaredProviderSeverity \= "ERROR" in the Metro DSL to prevent legacy injections.8 | Rely on Metro's compiler analysis and topological sorting to catch missing bindings or cycles before code generation.7 |

## **Testing Strategy in a Metro-Enabled Codebase**

Migrating to a compile-time DI architecture simplifies the testing pipeline by removing the need for global framework registries or mutable runtime states.1

### **Frame-Agnostic Unit Testing**

Because Metro relies on standard constructor injection, unit tests can instantiate classes directly without initializing any DI container.1 Mocking libraries or manual test doubles can be passed directly into constructors, making tests decoupled from the DI framework.1

Kotlin  
import kotlin.test.Test  
import kotlin.test.assertTrue

class UserServiceTest {  
      
    @Test  
    fun testUserAuthenticationFlow() {  
        // Direct constructor invocation with a fake dependency; no DI setup required   
        val fakeAuthService \= FakeAuthService()  
        val controller \= SessionController(fakeAuthService)

        controller.authenticate("user\_name", "secure\_password")  
        assertTrue(fakeAuthService.wasInvoked)  
    }  
}

### **Integration and End-to-End Testing via Dynamic Graphs**

For integration or end-to-end tests where the entire application graph must be initialized, developers can use Metro’s dynamic graph factories.17 This enables tests to override specific production bindings (such as swapping a production networking service for a fake implementation) using the createDynamicGraphFactory intrinsic.17

Kotlin  
import dev.zacsweers.metro.createDynamicGraphFactory  
import kotlin.test.BeforeTest  
import kotlin.test.Test  
import kotlin.test.assertNotNull

@BindingContainer  
object TestNetworkModule {  
    @Provides  
    fun provideFakeHttpClient(): HttpClient {  
        return FakeHttpClient(configuredResponse \= "Test Payload")  
    }  
}

class EndToEndSystemTest {  
      
    private lateinit var testGraph: ApplicationGraph

    @BeforeTest  
    fun setup() {  
        // Instantiate the application graph while overriding its production network module   
        testGraph \= createDynamicGraphFactory\<ApplicationGraph.Factory\>(TestNetworkModule)  
           .create(AppConfig(environment \= "Test-Sandbox")) \[17\]  
    }

    @Test  
    fun testSystemDataResolution() {  
        val service \= testGraph.apiService  
        assertNotNull(service)  
    }  
}

By transitioning the project’s dependency resolution model from Koin's runtime registry to Metro's compile-time validation framework 1, development teams shift the responsibility of verifying dependency safety to the compiler.1 This transition eliminates startup injection crashes, ensures robust modular boundaries across target platforms 2, and improves compile-time and runtime performance.1
